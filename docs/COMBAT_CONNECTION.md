# Optional Combat Tool connection

World Builder and DnDGameTool remain independent applications. Run both APIs only when you want to exchange data. Start World Builder normally; its existing FastAPI app now exposes `/integrations/combat` routes. In the combat app's **Admin** sidebar page, find **World Builder connection**. Its enable switch saves automatically; edit and save the API URL (normally `http://localhost:8000`) and browser URL (normally `http://localhost:5173`). Restart both updated APIs and refresh both frontends first.

In a campaign's Story Planner, edit a plot point and use **Attach combat encounter**. Prepare a roster using world PCs/NPCs or generic named combatants, with allegiance, quantity, optional HP/AC/level, location and a battle-map image. Saving preserves the plot point's existing story content and ID. **Open in Combat Tool** opens its import page; the combat app URL is configurable and defaults to `http://localhost:1212`. Loading campaigns selects that plot point, and a reviewed import creates/updates its combat scene. Characters can be linked to already entered combat units. Existing combat HP/statistics remain under the combat app's control.

Battle-map image bytes can be copied from this repo's `frontend/public` directory, the selected world's directory, or embedded base64 raster images. PNG/JPEG/WebP/GIF are supported up to 10 MB. An external image URL needs a local copy before sharing. Schematic canvases, markers and map drawings remain here. NPC references, including DM secrets, are saved privately in the combat app for offline use; refreshing is explicit and does not alter combat statistics.

Maps can also be used as dungeon backgrounds in DnDGameTool. In a map's edit sidebar, the **Player View** tab lets you upload or replace a background image, set a fog color, and enable fog of war. This works with either an uploaded image or the schematic canvas. With fog enabled, draw reveal areas around explored rooms or corridors, then choose **Update Player View**. World Builder exports two aligned PNGs with identical dimensions: a full DM map (visible markers including DM-only markers, without fog or masks), and a player map (public markers only, with fog, reveal cutouts, and explicit masks). Both are sent together. The combat DM can place enemies anywhere on the full dungeon; hidden enemies appear faded when **Show hidden tokens (DM only)** is enabled. **Preview player map** switches only the DM preview to the fogged image and the public token/card filtering. The player screen always receives the player image. Token reveals remain manual: drawing fog reveals here does not automatically reveal combat enemies.

Sprite markers are baked into both exports with their original proportions, size, rotation and mirroring. Public exports still exclude DM-only/hidden markers and apply fog and masks over the artwork. Sprites are fetched fresh for each publish to avoid reusing the editor's non-CORS image cache. A missing or unreadable assigned sprite stops publishing with its path in the error; the previous combat background remains in place. Markers without assigned sprites retain their normal symbol. Refresh World Builder and choose **Update Player View** to replace an older circle-only export; no combat API change is needed for this sprite fix.

Combat tokens, HP, positions, grid settings, manual background width and pan/zoom remain under DnDGameTool's control. Later fog updates replace the image without clearing units or resetting the camera. **Clear Player View** / **Restore encounter background** restores the encounter background while retaining units. Publishing requires DnDGameTool's API to be reachable (default `http://localhost:3000`; `1212` is the browser UI port). After installing these changes, restart the combat API, refresh both frontends and player windows, and publish the dungeon once to create the DM/player pair. An old combat API produces an explicit update/restart message; the publisher never falls back to sending the full dungeon as a public image.

The combat app's **Review encounter results** dialog sends an explicitly reviewed summary, optional outcomes and session number. This app appends one `story.combat_results` entry and a linked player action visible in campaign/session history. The player action remains unreviewed for story consequences. Sending the same result ID and payload again is a no-op. A conflicting reuse is rejected. Existing NPC records, plot-point statuses and clocks are never automatically changed. Legacy `StoryContent` remains supported and is not replaced by a result import; campaigns with that legacy story need the Story Planner before receiving summaries.

Reload an already open campaign after sending results. A stale entity or entity-YAML save that drops newly imported history returns 409. The ordinary single-worker API serializes entity-editor writes with result appends. Full YAML repair/backup restoration remains an explicit administrative operation. Existing YAML fields are retained when appending a result, and the existing YAML service backs up the source first. The integration adds optional fields; no authored world data is migrated on startup.

Exchange endpoints: `GET /integrations/combat/catalog`, `GET /integrations/combat/characters/{entity_id}`, `GET /integrations/combat/maps/{map_id}/image`, `POST /integrations/combat/results`. These are intended for the existing trusted local DM applications. Paired map publishing uses DnDGameTool's `POST /player/map/pair`: JSON `{ playerImage, dmImage }` contains raw base64 PNG bytes, with URL-encoded `X-Map-Name` and `X-Map-Id` headers. Both PNGs must be at most 10 MB, 4096 pixels per side and 16 million pixels, with identical dimensions. The old `POST /player/map` PNG endpoint remains compatible with older publishers. `/player/state` contains only the player image and revealed tokens. The full image is served separately at `/dm-map/:name` and omitted from the normal background catalog.

Published player maps update one local background per source map and selected combat campaign. Each push sends the map ID, so later fog-of-war reveals and map renames update the same background. The combat app keeps its camera framing and refreshes both images automatically. One public background entry is shown; its matching DM image is stored in the hidden `.dm-maps` subdirectory. The trusted DM settings record adds `playerMap.dmBackground` and `dmRevision`; neither enters the player feed. Camera broadcasts continue to use the public background filename for both views, so previewing the DM image does not change the synchronization scope. Older publishers without a map ID match by map name. Historical background copies created by earlier versions are kept.
